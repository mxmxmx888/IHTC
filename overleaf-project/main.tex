\reportsection{Aim}

This experiment compares an MDEO-Cloud implementation with a Python-based optimiser for the International Hospital Timetabling Competition (IHTC) scheduling problem~\cite{ceschia2025ihtc}. Both address the same integrated hospital-planning problem. They assign patient admission days, rooms, and operating theatres, then allocate nurses to the resulting room-day-shift demand.

The evaluation covers feasibility, schedule quality, and the computational effort required to obtain a schedule. Both approaches use the same IHTC benchmark instances and input data. MDEO-Cloud runs stop after 300 generations, even when the final candidate set has not converged. Runtime interpretation also accounts for execution conditions, particularly the different thread allocation used for MDEO-Cloud Test~10.

The study records patient-admission outcomes, resource use, nursing coverage, constraint violations, and search-performance measures. It compares results across the selected benchmarks and examines the practical implications of model-driven optimisation in MDEO-Cloud for hospital scheduling.

\reportsection{Controlled Variables}

Both implementations use the same IHTC benchmark instances and input data, holding the scheduling problem constant while the implementation varies. Runtime, feasibility, and solution quality are the experimental outcomes.

\begin{itemize}
    \item \textbf{Patients and occupants:} priority, release and due dates, length of stay, surgery duration, assigned surgeon, room compatibility, and existing occupants.
    \item \textbf{Nursing data:} nurse skill levels, shift availability, maximum workload, and daily patient demand.
    \item \textbf{Surgical resources:} daily surgeon availability and operating-theatre capacity.
    \item \textbf{Room resources:} capacity, compatibility requirements, and initial occupancy.
    \item \textbf{Planning structure:} decision horizon, available rooms, shift definitions, and IHTC scheduling rules.
\end{itemize}

\reportsection{Problem Definition}

The IHTC problem combines patient scheduling with nurse assignment. Scheduling decides whether each patient is admitted and, if so, assigns an admission day, room, and operating theatre. The admission day must fall within the patient's release and due dates and respect assigned surgeon and theatre availability.

Room constraints apply across the full stay. Each occupied room-day must have capacity, and patients from different age groups cannot share a room on the same day. Existing occupants consume room capacity and generate nursing demand but are fixed inputs, not scheduling decisions.

Admitted patients and their daily demand records define the active room-day-shift slots. A nurse can fill a slot only when available for that shift and qualified for its skill requirement. Allocation is assessed through coverage, uncovered workload, workload excess, and workload balance~\cite{ceschia2025ihtc}.

The metamodel represents patients, admissions, rooms and room-day availability, surgeons and their availability, theatres and their availability, nurses and working shifts, patient-day demands, hospitalisation shifts, and room-shift assignments. Transformations update candidate schedules, while objective functions evaluate them.

\reportsection{Optimisation Approaches}

Both implementations use the same instance set. MDEO-Cloud runs stop after 300 generations, and runtime comparisons require equivalent execution resources.

\subsection{MDEO-Cloud Solution}

MDEO-Cloud encodes each IHTC instance as a typed model containing patients, admissions, resources, availability records, nursing demands, and nurse assignments. Conversion initialises every mandatory patient as scheduled and linked to an admission, while optional patients remain unscheduled. Each candidate is stored as a complete model instance within the platform~\cite{krieger2026mdeo}.

NSGA-II~\cite{deb2002nsga2} searches candidate schedules through transformations that add, remove, or reassign admissions, rooms, admission days, theatres, and nurse assignments. Guards reject infeasible changes before execution. Once all mandatory patients have been admitted, a phase state moves the search from patient scheduling to nurse assignment.

Objective functions derive resource use and nursing demand from admissions and patient-day demand records. MDEO-Cloud optimises:

\begin{itemize}
    \item admitted patients, maximised;
    \item unscheduled-patient penalty and admission delay, minimised;
    \item room-capacity violation and missing mandatory admissions, minimised as redundant safeguards. Transformations still guard room capacity, and the phase-consistency constraint requires every mandatory patient to be admitted in a final candidate;
    \item aggregate surgeon and theatre operating-time excess;
    \item uncovered room-shifts and nursing workload;
    \item excess and imbalanced nurse workload;
    \item inactive nurse assignments;
    \item room-occupancy standard deviation.
\end{itemize}

\subsection{Python-Based Solution}
The Python-based implementation formulates the IHTC scheduling problem as a Mixed Integer Linear Programming (MILP) model built upon the PuLP optimisation library. This exact optimisation framework differs fundamentally from the heuristic NSGA-II evolutionary algorithm adopted in MDEO-Cloud. All hard constraints laid down by the IHTC competition regulations are explicitly encoded as linear equalities and inequalities to guarantee the feasibility of generated schedules.

The objective function adopts a weighted single-objective minimisation structure which aggregates eight soft penalty terms aligned with the competition evaluation metrics, corresponding to soft constraints S1 to S8: unscheduled patient penalty, admission delay penalty, open operating theatre penalty, age-mixing penalty, skill mismatch penalty, excess nurse workload penalty, continuity-of-care penalty, and surgeon transfer penalty. Weight parameters for each cost component follow the official benchmark configuration to ensure a fair comparison across the two solution approaches.

The model comprises two sequential decision layers: patient admission and room allocation, followed by nurse assignment for room-day-shift slots. Binary decision variables are defined to represent patient admission status, room occupancy, operating theatre activation and nurse-room shift allocation. The Big-M linearisation technique is utilised to convert non-linear logical rules into standard linear constraints. PuLP invokes the open-source CBC solver to find optimal or near-optimal feasible solutions under pre-defined computational time limits.

In contrast to the iterative evolutionary search of MDEO-Cloud, the MILP approach can deliver mathematically provable optimal solutions given sufficient computational resources. Nevertheless, the quantity of variables and constraints expands rapidly as the instance scale grows, imposing substantial memory and runtime overhead for larger benchmark test cases.

\reportsection{Constraints}

\subsection{MDEO-Cloud Solution}

The MDEO-Cloud model uses one configuration-level constraint and guarded transformations. The constraint requires the search to reach the \texttt{NURSES} phase with every mandatory patient admitted. Transformation guards enforce the remaining scheduling and nurse-assignment conditions before changes are applied. Individual surgeon and theatre fit is guarded, while aggregate daily operating-time excess is treated as an objective.

\begin{itemize}
    \item \textbf{Phase consistency:} \texttt{nurseAssignmentPhaseConsistency} is non-zero in the \texttt{PATIENTS} phase. In \texttt{NURSES}, it returns the number of mandatory patients without an admission. A feasible final candidate must therefore reach \texttt{NURSES} and admit every mandatory patient. \texttt{mandatoryPatientsAdmitted()} is a helper, not a configured constraint.

    \item \textbf{Admission scope and uniqueness:} model conversion creates the mandatory admissions before optimisation. T1--T3 add only unscheduled, non-mandatory patients and prevent duplicate admissions. T4 removes optional patients, T5 and T7 can remove any scheduled patient, and T6 replaces optional patients. A missing mandatory admission makes the candidate infeasible through \texttt{nurseAssignmentPhaseConsistency}.

    \item \textbf{Admission window:} the admission day must fall between the patient's release and due dates, and the full stay must fit within the decision horizon.

    \item \textbf{Surgeon and theatre feasibility:} admission and move transformations retain each patient's assigned surgeon, require the surgery duration to fit the selected surgeon-availability record, and require positive theatre capacity on the selected day. Aggregate surgeon and theatre excess remains an objective measure.

    \item \textbf{Room compatibility:} patients cannot be assigned to incompatible rooms.

    \item \textbf{Full-stay room capacity:} every room-day across a patient's stay must have an available bed before admission or reassignment.

    \item \textbf{Age-group compatibility:} a room-day must be empty or occupied by one age group. Different age groups cannot share a room on the same day.

    \item \textbf{Room-state consistency:} admission, removal, and reassignment transformations update \texttt{occupiedBeds} across the full stay and restore \texttt{AgeGroup.EMPTY} when a room-day becomes unoccupied.

    \item \textbf{Phase control:} T4--T13 operate in \texttt{PATIENTS}, T14--T16 require \texttt{NURSES}, and T1--T3 can add optional patients in either phase. The transition to \texttt{NURSES} is available only after all mandatory patients are scheduled.

    \item \textbf{Nurse availability and skills:} a nurse requires a matching \texttt{NurseWorkingShift} for the target day and shift. The assignment is rejected when any contributing patient demand exceeds the nurse's skill level.

    \item \textbf{Active nurse assignments:} assignments require an admission and patient-day demand that create nursing demand. Duplicate assignments to the same room-day-shift are prevented.

    \item \textbf{Objective penalties:} the model minimises unscheduled-patient penalty, room-capacity violation, missing mandatory admissions, aggregate surgeon and theatre excess, nurse workload excess, uncovered room-shifts, uncovered workload, workload imbalance, inactive assignments, admission delay, and room-occupancy standard deviation. Room-capacity and missing-admission objectives are redundant safeguards alongside their hard enforcement.
\end{itemize}

\subsection{Python-Based Solution}
The Python-based MILP model strictly separates hard constraints (which cannot be violated under any feasible solution) and soft penalty constraints (permitted to be violated but incur additive cost within the objective function). All hard rules defined by the IHTC competition are encoded as linear equality and inequality constraints enforced by the solver. No constraint violation is allowed in any feasible schedule.

\begin{itemize}
    \item \textbf{Patient admission window}: The admission day of each scheduled patient must lie within the interval between the patient’s release date and due date. The complete length-of-stay period must not exceed the planning horizon.
    \item \textbf{Surgeon and theatre feasibility}: A patient may only be admitted on a day where their assigned surgeon has available operating capacity and the selected operating theatre possesses residual capacity on that day.
    \item \textbf{Room compatibility}: A patient cannot be allocated to any room marked within their incompatible room list.
    \item \textbf{Full-stay room capacity}: For every day covered by the patient’s stay, the assigned room must maintain spare capacity to accommodate the patient.
    \item \textbf{Room age-group compatibility}: Patients from distinct age groups cannot occupy the same room on the same day. This rule is implemented as a hard constraint.
    \item \textbf{Nurse availability}: A nurse can only be assigned to a room-day-shift slot if they hold a valid \textit{NurseWorkingShift} record for that exact day and shift.
    \item \textbf{Nurse skill compatibility}: The skill level of an assigned nurse must satisfy or exceed the maximum skill demand generated by patients within the corresponding room-day-shift.
    \item \textbf{Active nurse assignments}: Nurse allocation is only enabled for room-day-shift entries with active patient admissions and positive nursing demand. Multiple assignments of the same nurse to one room-day-shift are prohibited.
\end{itemize}

Resource excess conditions, age-group mixing, uncovered nursing workload, nurse workload overload, care continuity degradation and other performance metrics are not implemented as hard constraints. These rules correspond to soft constraints S1–S8, and all associated penalties are aggregated into the weighted objective function for minimisation.

\reportsection{Evaluation Metrics}

The evaluation classifies feasibility first, then reports solution quality and search performance. MDEO-Cloud feasibility is implementation-derived. No separate post-run validator is used. A final model is feasible when \texttt{nurseAssignmentPhaseConsistency} is zero, placing it in \texttt{NURSES} with every mandatory patient admitted, and when guarded transformations have preserved the required scheduling conditions. Runs that fail this classification after 300 generations are recorded as infeasible, while their diagnostics and objective values remain available.

\subsection{MDEO-Cloud Solution}

\subsubsection{Feasibility Metrics}

\begin{itemize}
    \item \textbf{Final feasibility:} zero \texttt{nurseAssignmentPhaseConsistency} and a state reached through guarded transformations.
    \item \textbf{Hard diagnostic:} final room-capacity status. Admission windows, room compatibility, age-group compatibility, and nurse-assignment rules are guarded during the search but are not reported as separate post-run violation counts. Theatre and surgeon operating-time excess and uncovered workload are reported as objectives. Nurse workload excess remains in the raw Pareto output.
    \item \textbf{Mandatory-patient completion:} proportion of mandatory patients with an admission.
\end{itemize}

\subsubsection{Patient Scheduling Metrics}

\begin{itemize}
    \item Optional patients admitted, by number and proportion.
    \item Optional patients left unscheduled.
    \item Total and mean admission delay from release date to admission.
    \item Operating theatres open per day.
    \item Theatres used by each surgeon per day.
    \item Room age-group compatibility, enforced by guards and not reported as a post-run violation count.
\end{itemize}

\subsubsection{Nurse Assignment Metrics}

Raw Pareto output retains uncovered room-shifts, uncovered workload, nurse workload excess, and nurse workload imbalance. Only uncovered workload appears in the final results table. It measures workload from active room-shift slots without nurse cover. The other three values remain available in the raw output.

\begin{itemize}
    \item \textbf{Nurse skill compatibility:} transformation guards enforce the required skill level. \texttt{totalSkillLevelViolation()} is defined and imported but is neither a goal objective nor a formal constraint, so it is not reported numerically.
\end{itemize}

\subsubsection{Reported Resource Measures}

\begin{itemize}
    \item \textbf{Reported hard diagnostic, room capacity:} final room-capacity status in Table~\ref{tab:feasibility-results}.
    \item \textbf{Reported objective measures, theatre and surgeon operating-time excess:} aggregate excess values in Table~\ref{tab:feasibility-results}.
\end{itemize}

Room-bed, theatre, and surgeon utilisation ratios were not exported and are omitted.

\subsubsection{Search Performance Metrics}

Each run reports:

\begin{itemize}
    \item wall-clock runtime, completed generations, and candidate evaluations;
    \item executed and skipped transformations and the Pareto-solution count;
    \item final feasibility status and objective and diagnostic values.
\end{itemize}

\subsubsection{Reporting}

Results cover feasibility, patient scheduling, nurse assignment, resource measures, and search performance. They are reported separately rather than as a composite score. Since the implementations can encode the same condition as a hard requirement or a soft penalty, objective values and penalty totals are interpreted within their respective implementations. Raw MDEO-Cloud outputs also contain missing mandatory admissions, inactive nurse assignments, room-occupancy standard deviation, and transformation skip rate.

\subsection{Python-Based Solution}
Evaluation of the MILP implementation follows the same two-stage framework: feasibility verification followed by solution quality assessment. A candidate schedule is only regarded as valid if all hard constraints are fully satisfied without violation. All feasible solutions are then evaluated using the unified official IHTC weighted cost function, which aggregates the eight soft penalty components S1–S8 as the primary comparison metric.

The evaluation metrics are categorised consistently with the MDEO-Cloud benchmark, covering feasibility statistics, patient scheduling outcomes, nurse assignment performance and resource utilisation. Metrics specific to evolutionary search, such as generation count and transformation attempts, are omitted, as they are not applicable to the exact MILP solving paradigm.

Solver performance is recorded via wall-clock runtime and final solver status (optimal, feasible or time-limited). Detailed per-instance soft penalty breakdowns are recorded to support cross-method comparison against results obtained from MDEO-Cloud.

\reportsection{System Hardware}

MDEO-Cloud ran on an AMD Ryzen 9 9950X3D system with 96\,GB of DDR5 RAM. Tests~01--09 used a development virtual machine on this system with a smaller CPU-thread allocation, which was not retained.

Test~10 used three MDEO execution nodes with eight threads each, for 24 threads total. The additional threads were necessary because the earlier allocation would have made the run impractically long. Its runtime is therefore an annotated large-instance result, separate from the directly comparable Tests~01--09 scalability observations.

Test~10 also had 60-second script and model-transformation safeguards. Neither was reached, so neither affected termination or the reported result.

\reportsection{Experiment Procedure}

Each benchmark instance was run once per framework. MDEO-Cloud Tests~01--09 used the development virtual machine allocation, while Test~10 used additional CPU threads. Its 60-second safeguards were never reached.

\subsection{MDEO-Cloud Solution}

\begin{itemize}
    \item \textbf{Instance collection:} IHTC test instances were gathered.
    \item \textbf{Model conversion:} each instance was converted into a valid MDEO-Cloud model.
    \item \textbf{Model validation:} converted models were checked for required entities, links, and availability objects.
    \item \textbf{Configuration:} population size, evolutions, mutation settings, and other solver parameters were set before execution.
    \item \textbf{Termination:} MDEO-Cloud had no wall-clock cutoff. Every run stopped after 300 generations, regardless of convergence, and its duration was recorded. Test~10 had 60-second script and transformation safeguards, neither of which was reached.
    \item \textbf{Optimisation execution:} the search used the implemented metamodel, transformations, constraint, and objectives.
    \item \textbf{Schedule generation:} final solutions included patient admissions and room-shift nurse assignments.
    \item \textbf{Result export:} schedules were exported or converted for analysis.
    \item \textbf{Data collection:} objective and violation values, runtime behaviour, and final schedule statistics were recorded.
\end{itemize}

\subsection{Performance and Scalability}

\subsubsection{MDEO-Cloud Solution}

All Tests~01--10 stopped after 300 generations and recorded 59,900 candidate evaluations. The evaluation count records search activity and did not control termination.

Tests~01--09 provide the comparable runtime trend because they used the same development virtual machine allocation. Cases with 37--62 patients took 363--647~s, while cases with 111--173 patients took 1,454--3,728~s. Test~10 had 525 patients, used additional CPU threads, and took 32,676~s, or about 9~hours and 5~minutes. Its 60-second safeguards were never reached. It remains an annotated large-instance observation, separate from the Tests~01--09 scalability trend.

Patient count alone did not determine runtime. Test~09, with 146 patients, took longer than Test~08, which had 173. The difference follows the variation in executed and skipped transformations shown in Table~\ref{tab:mdeo-diagnostics}, but one run per instance cannot isolate a single cause. Test~10 has the same limitation because its larger instance used a different execution allocation. Its runtime reflects both factors. The unused safeguards had no effect on termination or the final result.

Test~10 showed unclear convergence at the 300-generation limit. The search was still applying transformations and retaining trade-offs between admissions and violation measures. The 349-admission schedule is therefore the final state of that run.

MDEO results use no single score. One run per instance provides no basis for means, standard deviations, or statistical significance claims.

\subsection{Comparison with Existing GIPS-Based Results}

The published GIPS-based MILP study provides contextual evidence~\cite{kratz2025gips}. It evaluates all 30 public IHTC instances using Gurobi in a MILP pipeline, while this MDEO-Cloud study evaluates Tests~01--10 using NSGA-II.

The GIPS study reports feasible solutions for all 30 public instances within the original 10-minute limit and proves optimality for two under a relaxed budget. MDEO-Cloud reports feasible schedules for all 10 tested instances. The different settings prevent direct rankings of runtime or benchmark coverage. Tests~01--09 remain the internally comparable MDEO-Cloud runtime observations, while Test~10 is excluded from contextual runtime comparison because of its different CPU-thread allocation.

\reportsection{Limitations}

\subsection{General Limitations}

\begin{itemize}
    \item \textbf{Benchmarking scope:} the evaluation covers only IHTC 2024 instances, whose resources, planning horizons, and demand patterns may not represent all hospital settings.
    \item \textbf{Scope of conclusions:} results from the selected benchmarks do not establish that either implementation is superior across healthcare scheduling problems.
    \item \textbf{Published-baseline comparability:} GIPS-based results provide contextual evidence because they use a different solver paradigm, time-limit policy, and instance coverage.
    \item \textbf{Implementation differences:} different internal representations, search operators, and objective decompositions require implementation-specific interpretation.
    \item \textbf{Single-run sampling:} each instance was run once because larger cases are expensive to repeat. The results are observed outcomes, without means, medians, confidence intervals, or statistical claims about stochastic-search reliability.
    \item \textbf{Model and conversion fidelity:} results depend on accurate IHTC-to-model conversion and complete constraint and objective definitions.
\end{itemize}

\subsection{MDEO-Cloud Solution}

\begin{itemize}
    \item \textbf{Runtime comparability:} MDEO-Cloud stops after 300 generations, not a wall-clock limit. Runtime therefore measures one fixed-length search and does not represent equal computational effort across implementations.
    \item \textbf{Test~10 conditions:} Test~10 used additional CPU threads. Its 60-second safeguards were never reached and had no effect on termination or results. It remains an annotated large-instance observation, separate from the Tests~01--09 scalability trend and cross-framework runtime comparisons without equivalent resources.
    \item \textbf{Fixed generation budget:} Test~10 reached 300 generations without clear convergence. A larger search budget could produce different Pareto candidates.
\end{itemize}
